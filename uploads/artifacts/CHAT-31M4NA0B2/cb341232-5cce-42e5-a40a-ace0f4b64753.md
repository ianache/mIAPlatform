## 1. Visión General del proyecto  

**Objetivo**: Construir un modelo de Machine Learning (ML) que combine :

| Fuente | Tipo de información | Uso en el modelo |
|--------|---------------------|------------------|
| **Historial de robos de vehículos** (bases de datos de la policía, aseguradoras, concesionarias) | Eventos georreferenciados y temporales de hurtos | Etiqueta de riesgo (probabilidad de robo) |
| **Zonas de alta criminalidad** (índices de seguridad ciudadana, datos abiertos de gobiernos locales) | Mapas de calor, indicadores socio‑económicos | Variables de entorno que aumentan la exposición al riesgo |
| **Patrones de conducción** (telemática del vehículo, OBD‑II, apps de movilidad) | Velocidad, frenadas bruscas, rutas frecuentes, horarios | Variables conductuales que modulan la vulnerabilidad |

El resultado será una **API de scoring** que, para cada vehículo o cliente, entregue una probabilidad de robo y recomendaciones (ej.: “evite circular por X zona a las 22 h”).

### 2.1. Principios de diseño  

| Principio | Cómo se implementa |
|-----------|--------------------|
| **Seguridad por diseño** | *Zero‑Trust* entre servicios (mutual TLS via Istio), **IAM** basado en roles (principio de menor privilegio). |
| **Resiliencia** | Pods con *PodDisruptionBudgets*, *Circuit Breakers* y *Retries* en el gateway. |
| **Observabilidad** | *OpenTelemetry* → Prometheus/Grafana + Loki para logs + Jaeger para trazas. |
| **Compliance** | Políticas de retención (ISO 27001 A.8), cifrado en tránsito y reposo, auditoría de accesos (ISO 27001 A.12.4). |
| **Escalabilidad** | Kubernetes (autoscaling HPA), Kafka para ingestion en tiempo real, Spark para entrenamiento distribuido. |
| **Reusabilidad** | Cada dominio (historial, zona, conducción) expuesto como *bounded context* con su propio micro‑servicio. |

## 4. Flujo de datos y entrenamiento del modelo

### 4.1. Ingesta  

1. **Robos** → Conector Kafka (API de la policía / CSV de aseguradoras).  
2. **Zonas de criminalidad** → Descarga nightly de datasets open‑data → S3 raw → Trigger Airflow.  
3. **Telemetría** → MQTT → Kafka → Topic `vehicle.telemetry`.  

Cada mensaje se escribe **encriptado (TLS)** y se **etiqueta** con `sensitivity=high` para aplicar políticas de retención.

### 4.2. Transformación (Airflow DAG)  

```python

    # 3️⃣ Agregar métricas telemáticas (avg_speed, hard_brakes)

```

- **Geocodificación** mediante *PostGIS* (ISO 27016‑A.6 – protección de datos financieros/seguridad).  
- **Normalización** y *feature scaling* en *dbt*.

### 4.3. Entrenamiento  

- **Algoritmo**: *Gradient Boosted Trees* (XGBoost) + *Graph Neural Network* para capturar relaciones entre zonas adyacentes.  
- **Validación**: *Stratified K‑fold* manteniendo distribución temporal.  
- **Métricas**: AUC‑ROC, *Recall* > 0.85 (priorizamos minimizar falsos negativos).  

**Pipeline** (Databricks Notebook → MLflow Run):  

```python
import mlflow
with mlflow.start_run():
    model = xgboost.train(params, dtrain, num_boost_round=200)
    mlflow.log_params(params)
    mlflow.log_metric("auc", auc_score)
    mlflow.sklearn.log_model(model, "model")
```

- **Control de versiones**: Cada run se marca con `git_commit`, `data_version` (LakeFS).  

### 4.4. Deploy de Inferencia  

- **Canary release**: 5 % de peticiones a nueva versión; métricas de latencia y drift monitorizadas.  
- **Feature flag** (LaunchDarkly) para activar/desactivar en concesionarias específicas.

## 5. Seguridad y cumplimiento ISO 27001 / ISO 27016  

| Control ISO 27001 | Implementación concreta | Comentario |
|-------------------|------------------------|------------|
| **A.5.1 Políticas de seguridad de la información** | Documentos en Confluence; aprobados por CISO; accesibles sólo a roles *Security* y *Architecture* | Base para auditorías |
| **A.6.1 Organización interna** | Comité de gestión de riesgos (quarterly) que revisa *risk register* del modelo (bias, privacy). | ISO 27016 – gestión de riesgos financieros |
| **A.7.2 Concienciación y entrenamiento** | Programa de e‑learning para desarrolladores (secure coding) y dealers (uso de la app). | |
| **A.8.2 Clasificación de la información** | Tag `sensitivity=high` para datos de robos; cifrado SSE‑AES‑256; DLP para evitar exportación. | |
| **A.9.1 Control de acceso** | RBAC en Kubernetes (RBAC + OPA/Gatekeeper); MFA en Keycloak. | |
| **A.10.1 Criptografía** | TLS 1.3 en todas las comunicaciones; claves rotadas cada 90 días (AWS KMS). | |
| **A.12.3 Protección contra malware** | Scaneo de contenedores (Trivy) en CI; whitelist de imágenes firmadas (cosign). | |
| **A.12.4 Registro de eventos** | Central logging (Loki) + SIEM (Elastic Security); retención 365 días. | |
| **A.14.2 Seguridad en el desarrollo** | *Static code analysis* (SonarQube), pruebas de penetración (OWASP ZAP) en cada release. | |
| **A.16.1 Gestión de incidentes** | Playbook de “Model Drift / Data Breach” con notificaciones automáticas a PagerDuty. | |
| **A.18.1 Cumplimiento** | Auditorías trimestrales con checklist ISO 27001; evidencia almacenada en SharePoint con retención legal. | |

### 5.1. Protección de datos personales (GDPR / LOPI)  

- **Pseudonimización** de datos de conductores antes de almacenarlos.  
- **Consentimiento** gestionado vía *Consent Management Platform* (OneTrust) integrado a la app.  
- **Derecho al olvido**: workflow de borrado en LakeFS que marca los objetos como “tombstone” y los elimina tras 30 días.
