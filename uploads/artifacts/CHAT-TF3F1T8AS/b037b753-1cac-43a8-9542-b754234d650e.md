## ¿Qué es una **cita externa** en el dominio de Concesionarias?

En el contexto de la arquitectura de concesionarias (sub‑proyecto *Arquitectura de Concesionarias*), **cita externa** se refiere a **cualquier reserva o programación de un servicio, prueba de manejo, entrega de vehículo u otro tipo de atención que sea solicitada por un cliente que no pertenece al personal interno de la concesionaria**.  

En otras palabras, es una cita **generada desde fuera del sistema interno** (por ejemplo, a través de la web, una app móvil, un call‑center, un partner o una integración con terceros) y que necesita ser gestionada, almacenada y trazada por el ecosistema de la concesionaria.

---

## Componentes clave de una cita externa

| Componente | Descripción | Comentario típico en Qdrant |
|------------|-------------|------------------------------|
| **Identificador de cita** | UUID o número secuencial que la hace única. | `cita_id` (keyword) |
| **Tipo de cita** | Servicio, prueba de manejo, entrega, inspección, etc. | `cita_tipo` (enum) |
| **Origen** | Canal por el que se creó: web, app, call‑center, partner, API externa. | `cita_origen` (keyword) |
| **Cliente** | Datos del cliente (nombre, documento, teléfono, email). | `cliente` (object) |
| **Vehículo** | VIN, modelo, versión, año, color (si la cita está asociada a un vehículo concreto). | `vehiculo` (object) |
| **Fecha / hora** | Momento programado para la atención. | `cita_fecha_hora` (datetime) |
| **Estado** | Pendiente, confirmada, cancelada, completada, no‑asistida. | `cita_estado` (enum) |
| **Observaciones** | Comentarios del cliente o del asesor (p.ej. “necesita cambio de aceite + filtro”). | `cita_observaciones` (text) |
| **Asignación** | Técnico o asesor asignado, bay/puerta de servicio, recursos requeridos. | `cita_asignacion` (object) |
| **Metadatos de trazabilidad** | Usuario que creó la cita, timestamps de creación/modificación, origen de la solicitud (IP, ID de sesión). | `audit_*` (datetime/keyword) |

## Flujo típico de una cita externa

1. **Captura del requerimiento**  
   - El cliente rellena un formulario en la web, usa la app móvil o llama al call‑center.  
   - El sistema externo (CRM, portal de clientes, partner) envía una petición **REST/GraphQL** o **mensaje en cola** (Kafka, RabbitMQ) al *API Gateway* de la concesionaria.

2. **Validación y normalización**  
   - Se verifican datos obligatorios (identificación del cliente, VIN, disponibilidad).  
   - Se normaliza la hora solicitada a la zona horaria de la concesionaria y se comprueba la disponibilidad de recursos.

3. **Creación de la entidad de cita**  
   - Se persiste la entidad `CitaExterna` en la base de datos transaccional (PostgreSQL, MySQL).  
   - Se genera el `cita_id` y se asocian los objetos `Cliente` y `Vehículo` (si corresponde).

4. **Indexación en Qdrant (vector store)**  
   - La descripción libre de la cita (observaciones, motivos) se **vectoriza** mediante el modelo de embeddings que la arquitectura usa (p.ej. **sentence‑transformers**).  
   - El vector, junto con los metadatos estructurados, se inserta en la colección `citas_externas` de Qdrant.  
   - Esto permite búsquedas semánticas posteriores: “buscar citas que incluyan “revisión de frenos””.

5. **Notificación al cliente**  
   - Se envía confirmación vía email/SMS/WhatsApp con número de cita y datos relevantes.  
   - Si la cita es modificada o cancelada, se envía una notificación de actualización.

6. **Gestión operativa**  
   - El área de servicio consulta la agenda (UI interna) y puede **filtrar** por tipo, estado, técnico, etc.  
   - Se pueden ejecutar consultas **semánticas** en Qdrant para detectar citas “similares” (por ejemplo, agrupar todas las citas que mencionen “fugas de aceite” y priorizarlas).

7. **Cierre y trazabilidad**  
   - Al finalizar el servicio se actualiza el estado a *completada* y se añaden resultados de la intervención.  
   - Los vectores de la cita pueden actualizarse con la nueva información para que la búsqueda futura sea más precisa.

## Cómo está modelada la información de citas externas en Qdrant

### 1. Colección
- **Nombre:** `citas_externas`
- **Dimensionalidad:** 768 (embeddings de `sentence‑transformers/all‑MiniLM‑L6‑v2`, aunque puede variar según el modelo seleccionado).
- **Metric:** *Cosine* (para búsquedas semánticas de similitud).

### 2. Campos de *payload* (metadatos)

| Campo | Tipo | Uso típico |
|-------|------|------------|
| `cita_id` | `keyword` | Búsqueda exacta, linking con la base relacional. |
| `cita_tipo` | `keyword` | Filtros por tipo de servicio. |
| `cita_origen` | `keyword` | Analítica de canales (web vs call‑center). |
| `cliente_id` | `keyword` | Enlaza con la entidad `Cliente`. |
| `vehiculo_vin` | `keyword` | Enlaza con la entidad `Vehículo`. |
| `cita_fecha_hora` | `datetime` | Rango temporal para agendas. |
| `cita_estado` | `keyword` | Filtrado de pendientes/completadas. |
| `cita_asignado_a` | `keyword` | Asignación de técnico o asesor. |
| `cita_observaciones` | `text` | Texto libre que se vectoriza. |
| `audit_created_at` | `datetime` | Auditoría. |
| `audit_created_by` | `keyword` | Auditoría. |

> **Tip:** Los campos **keyword** son indexables y permiten filtros rápidos (`filter: {must: [{key: "cita_estado", match: {value: "pendiente"}}]}`), mientras que el **vector** habilita la coincidencia semántica sobre `cita_observaciones`.

### 3. Operaciones frecuentes

| Operación | Ejemplo de uso |
|-----------|----------------|
| **Insert** | Cuando se crea una cita externa. |
| **Update** | Cambiar estado, reasignar técnico o actualizar observaciones. |
| **Search (semantic)** | `search(vector, top=5, filter={must: [{key: "cita_tipo", match: {value: "servicio"}}]})` → devuelve las 5 citas más semánticamente parecidas que sean de tipo *servicio*. |
| **Delete** | Cuando una cita se elimina por error (se elimina en la base relacional y se hace `delete_by_id` en Qdrant). |

## Beneficios de gestionar la cita externa con Qdrant

| Beneficio | Por qué importa para la concesionaria |
|-----------|---------------------------------------|
| **Búsqueda semántica** | Los asesores pueden encontrar rápidamente citas “relacionadas” aun cuando la redacción sea distinta (p.ej., “revisión de frenos” vs “chequeo del sistema de frenado”). |
| **Análisis de tendencias** | Al filtrar por `cita_origen` y agrupar vectores, se detectan patrones emergentes (p.ej., aumento de citas por “carga de batería”). |
| **Recomendación proactiva** | Al comparar vectores de citas pendientes con históricos de problemas, el motor puede sugerir servicios adicionales (p.ej., “el cliente ha mencionado ruido al frenar; ofrezca inspección de discos”). |
| **Escalabilidad** | Qdrant está diseñado para manejar millones de vectores y consultas de baja latencia, lo que permite que la agenda sea siempre responsiva. |
| **Sincronía con el Core** | Al mantener `cita_id` como clave de unión, cualquier cambio en la base transaccional se refleja rápidamente en el vector store mediante eventos (CDC). |

## Preguntas frecuentes (FAQ)

| Pregunta | Respuesta breve |
|----------|-----------------|
| **¿Puedo buscar citas por cliente sin conocer el `cita_id`?** | Sí. Usa un filtro por `cliente_id` o realiza una búsqueda semántica sobre `cita_observaciones` combinada con ese filtro. |
| **¿Qué pasa si el modelo de embeddings cambia?** | Se debe **re‑indexar** la colección: exportar los payloads, volver a generar los vectores con el nuevo modelo y re‑importarlos. Qdrant permite *replace* de vectores sin perder los metadatos. |
| **¿Cómo manejo la confidencialidad de datos personales (GDPR)?** | Solo los campos estrictamente necesarios (`nombre`, `email`, `teléfono`) se almacenan en la base relacional. En Qdrant, se guarda **solo** el `cita_id` y los vectores; los textos que contengan datos personales pueden ser anonimizados antes de vectorizar. |
| **¿Se pueden crear alertas automáticas cuando hay muchas citas “similares” en un corto período?** | Sí. Un proceso de *streaming* (por ejemplo, usando Kafka + Flink) puede ejecutar una búsqueda semántica cada X minutos y, si el número de coincidencias supera un umbral, disparar una notificación al responsable de operaciones. |
| **¿Cuál es la política de retención de datos en Qdrant?** | Normalmente se conserva el vector mientras la cita exista en la base transaccional. Si la cita se elimina (p.ej., después de 2 años sin actividad), también se elimina el vector mediante `delete_by_id`. |

## Resumen rápido (cheat‑sheet)

| Acción | Endpoint / Código (ejemplo) | Comentario |
|--------|-----------------------------|------------|
| **Crear cita externa** | `POST /api/citas` → guarda en DB y llama a `qdrant_client.upsert(collection="citas_externas", points=[{id: cita_id, vector: embedding, payload: {...}}])` | Genera `cita_id` y vectoriza `observaciones`. |
| **Actualizar estado** | `PATCH /api/citas/{cita_id}` → actualiza DB y `qdrant_client.update(payload={cita_estado: "cancelada"})` | No se modifica el vector (solo el payload). |
| **Buscar por similitud** | `GET /api/citas/search?text=“fuga aceite”&tipo=servicio` → vectoriza el texto de búsqueda y llama a `qdrant_client.search(vector, top=10, filter={must:[{key:"cita_tipo", match:{value:"servicio"}}]})` | Devuelve IDs y puntuaciones de similitud. |
| **Eliminar cita** | `DELETE /api/citas/{cita_id}` → elimina en DB y `qdrant_client.delete(ids=[cita_id])` | Mantiene consistencia. |
| **Obtener agenda del día** | `GET /api/citas?fecha=2026-04-06` → query DB + filtro `cita_fecha_hora` | Qdrant no se usa aquí (es filtro estructurado). |
